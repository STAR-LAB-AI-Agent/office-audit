# AI Office 文档审计 答辩与复测提纲

- 项目选题：#03 AI Office 文档审计
- 答辩时长：约 5 分钟
- 适用对象：专业实习结题答辩、现场技术展示与宿主环境复测

## 一、五分钟答辩陈述时间表

### 0:00 - 0:40 | 课题定位与审计范围
- **选题背景**：本项目为智能体开发实战课程选题 `#03 AI Office 文档审计`，聚焦高校学生作业、学术报告及日常公文在提交前的自动化合规自检。
- **功能定位**：面向 Word `.docx` 格式文档，提供**只读、轻量、可复现**的静态结构与排版规则审计。
- **边界声明**：专注排版结构与格式规范，不修改原文内容，不负责文档语义逻辑推导，不作为 PII 隐私合规或全局安全检测工具。

### 0:40 - 1:30 | 系统架构与实现方案
- **架构解耦**：采用“跨宿主 Skill 入口 + 统一 Python 确定性内核”设计。各智能体宿主（Codex, Nanobot, Claude Code, Antigravity）共用位于 `scripts/audit_docx.py` 的同一套内核，避免不同宿主产生规则分裂。
- **三种审计模式**：
  1. `full`：结构、字段、排版全量合规审计；
  2. `structure`：专注标题层级连贯性及用户指定必需章节（不盲目假设统一格式）；
  3. `fields_format`：专注空白段落、空白单元格、模板占位符与字体格式离群。
- **安全与防护机制**：内置输入合法性校验、输出路径防覆写检查（严格拒绝输出等于输入或硬链接冲突）、以及基于文件大小与解压比例的资源消耗预检。

### 1:30 - 2:30 | 现场/录屏效果演示
- **演示物料**：基于无敏感信息的合成测试文档（`scripts/demo_audit.py` 生成）。
- **演示流程**：
  1. 命令行/终端单条指令启动审计，展示标准 JSON 及 Markdown 报告；
  2. 重点展示问题定位能力：提供结构化位置（正文段落索引、表格行/列）及**人工核对所需的上下文前后文字**；
  3. 展示**未审计对象清单**：对图片、复杂公式、文本框、OLE 嵌入对象等，不静默忽略，而是显式列出位置与潜在盲区。
- **时间控制**：演示视频控制在 45-55 秒内，现场优先依评委老师偏好选择播放录屏或命令行实跑。

### 2:30 - 3:30 | 核心工程演进与降噪突破
- **真实场景挑战**：在引入真实外部样本文档测试时，早期版本出现大量误报（例如正常的封面大字号、表格内居中排版被判为异常格式；正常的排版空行被判为空白错误）。
- **降噪算法优化**：
  1. **角色细分与分列基线**：将正文划分为标题候选、正文段落、表格单元格等角色，并针对表格建立独立的列基线，避免跨列/跨角色比较；
  2. **连续空段聚合定位**：将分散的空行合并为连续空白段落组，单空行标记为 `info`，连续空行升级为待核对 `warning`；
  3. **内容载体识别**：纯图片或带公式单元格不再误报为空白。

### 3:30 - 4:20 | 验证体系与评测指标
- **单元测试**：本地环境（Python 3.12）全量 46 项单元测试 100% 通过（耗时约 6.6s），覆盖规则、CLI、防御机制与评测逻辑。
- **CI 自动化**：GitHub Actions（`audit-ci.yml`）在云端对 Python 3.10、3.11、3.12 三个版本完成矩阵构建与回归测试全部通过（最新 Run ID: 35195627461）。
- **受控评测**：15 组受控缺陷合成样例评测通过，$TP=8, FP=0, FN=0, TN=27$，Precision=100.0%, Recall=100.0%（已注明仅代表预设规则集，不代表真实文档召回率）。
- **真实文档回归**：12 份公开/外部样例回归测试无崩溃，审计前后原文档 SHA-256 哈希完全一致，精准识别并输出 33 处未审计对象。

### 4:20 - 5:00 | 独立安全案例总结与未来展望
- **安全案例调研**：独立完成《香港深度伪造视频会议诈骗案分析》，提炼核心安全启示——视听感知不能等同于业务授权凭证，大额支付必须依赖独立信道的双人多因素审批流程。
- **当前局限与未来展望**：
  1. 当前对复杂样式继承、混合富文本 run 级的排版识别仍有局限；
  2. 对文本框、形状、OLE 内部文字尚无法展开深度内容解析；
  3. 下一步优先推进真实文档的逐位置真值标签标注集建设，推动评测指标向真实场景对齐。

## 二、答辩核心问答（Q&A 预案）

### Q1：为什么要把项目做成 Skill，而不是一个纯粹的 Python 脚本？
**回答要点**：
脚本负责底层的确定性解析、规则匹配与标准数据输出；而 Skill 则规范了智能体（LLM Agent）在面向用户自然语言请求时，如何正确解析意图（选择 full、structure 还是 fields_format 模式）、如何传递参数、以及如何解释审计报告与边界限制。Skill 将确定性工具无缝融入了智能体工作流中，且本项目的单一内核架构保证了即使脱离 Agent 宿主，底层脚本依然能作为独立 CLI 高效运行。

### Q2：为什么不直接把整个 Word 文档全文喂给大语言模型（LLM）进行审计？
**回答要点**：
1. **确定性与可复现性**：文档排版、段落空行、样式跳级属于结构化规则，规则算法运行效率高、无随机幻觉，输出结果完全可复现；
2. **位置定位精度**：大模型对复杂长文本中的段落序号、表格行列坐标缺乏稳定精确定位能力，而 Python-docx 可以精确抓取底层 XML 节点位置；
3. **隐私与性能成本**：本地运行无需将全文上传至云端或消耗昂贵的模型 Token，极大降低数据泄露风险与调用延迟。

### Q3：外部真实样例只有 12 份，样本数量是否偏少？
**回答要点**：
真实样例的核心作用是**发现真实排版多样性并进行回归验证**（验证解析器鲁棒性、输入哈希一致性与未审计对象捕获）。因为真实样本目前缺乏人工逐点标记的真值标签（Ground Truth），盲目堆砌未标注样本无法计算客观的准确率/召回率。项目的量化指标由具有明确标签的 15 组受控样例支撑，二者定位互补。

### Q4：受控样例评测取得了 100% 的 Precision 和 Recall，这是否说明审计工具已经非常完美？
**回答要点**：
不能这样认为。在报告和文档中我们已做出了显式声明：受控样例的 100% 指标仅反映系统在**人工预设的已知确定性规则场景下**没有误报与漏报。真实业务文档中存在极其复杂的样式嵌套、人工随意换行以及非标准模板，真实世界的召回率必然低于受控评测。我们拒绝把合成测试集指标夸大为真实文档准确率。

### Q5：系统是否支持个人隐私信息（PII，如身份证号、手机号、邮箱）的合规审计？
**回答要点**：
目前版本**不支持且不承诺** PII 审计。本项目定位为“文档排版与结构规范质量自检”，而非隐私合规审计工具。虽然可以通过正则扩展手机号或身份证检测，但在未经过完备的消歧规则与上下文语义模型调优前，强行上线会导致极高误报率。因此明确将 PII 划归在当前系统边界之外。

### Q6：系统声称具备“资源消耗预检”，这是否能“绝对防御拒绝服务（DoS）或 Zip 炸弹攻击”？
**回答要点**：
不能称为“绝对防御”。系统目前实现了基于文件大小阈值（默认 50MB）、解压缩体积比与总大小限制、以及最大段落/表格数的**静态前置预检**。这能有效拦截常见的巨型畸形包与浅层 Zip 炸弹，但它只是应用层的输入过滤手段，并非操作系统级别的安全沙箱（Sandbox），不能阻止底层 C 解析库潜在的内存破坏漏洞。

### Q7：在复杂文档中，为什么有些字体差异没有被判定为“格式离群”？
**回答要点**：
这是为了控制误报率而做出的工程取舍。项目引入了“角色分组”与“主导样式阈值”机制：只有同组段落达到一定数量（如不少于 3 段），且存在过半数的主导样式时，才对偏离主导样式的段落报警；对于两三种字体旗鼓相当的段落，系统判定为“无绝对主导样式”，转为给出提示信息。这种设计显著减少了正常排版下的虚假告警。

### Q8：独立安全案例为什么选“香港深度伪造视频会议诈骗案”，它对智能体开发有何启示？
**回答要点**：
该案是 2024 年最典型的人工智能辅助社会工程学诈骗案例（涉案损失约 2 亿港元）。它表明 AI 安全威胁不只局限于模型本身的越狱或对抗样本，更在于 AI 生成伪造内容后进入真实业务审批链条导致的信任滥用。对智能体和自动化系统而言，核心启示在于：无论模型表现多么拟真，凡涉及高危资产操作（转账、文件删除、权限变更），都必须坚持“最小特权”与“独立信道双人复核”，绝不能仅凭单一视听凭证完成授权。

### Q9：当前 Skill 在 Codex、Nanobot、Claude Code 和 Antigravity 上的兼容性状态如何？
**回答要点**：
我们对不同环境的证据进行了严格的定性区分：
1. **Codex / Nanobot / Claude Code**：拥有 2026 年 9 月 11 日的端到端调用历史验收记录，在新一轮代码修改后建议按测试指引执行二次复测；
2. **Antigravity**：在当前开发环境中已完成端到端 CLI 脚本验证与输入哈希一致性、输出防护验证，但尚未在 Antigravity 原生 Agent Tool 层面由大模型自主调用验收，因此如实定性为“CLI 验证通过，未宣称自主 Agent 兼容”。

### Q10：答辩与演示视频录制为什么要求使用合成文档？
**回答要点**：
出于严格的数据合规与隐私保护考虑。真实学生作业或内部报告往往包含学生姓名、学号、联系方式或未公开实验数据。使用由 `scripts/demo_audit.py` 生成的专用合成文档，既能精确复现标题跳级、占位符、空单元格等典型缺陷，又能确保演示材料在公开答辩与视频录制中绝对不泄漏任何个人隐私与敏感数据。
