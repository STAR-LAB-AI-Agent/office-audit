# AI Office 文档审计：阶段1设计基线

## 1. 选题与课程要求对应

本项目选择课程任务书中的 `#03 AI Office 文档审计`。课程任务的基本目标是检查 Word/Office 文档的标题层级、空字段、缺失章节和基础格式，并输出结构化审计结果及建议；可选功能是支持自定义审计规则。阶段1只冻结范围和验收设计，不把尚未实现的能力写成已完成能力。

课程任务书规定的总体实践链路是“自然语言交互 + Python 开源项目 + Script/CLI + Skill”。本项目采用 `python-docx` 解析 `.docx`，以可独立运行的 Python CLI 为核心，用 `SKILL.md` 和 `agents/openai.yaml` 描述自然语言入口。暂不引入 nanobot、MCP、FastAPI 或 Telegram/Google Docs 等非必要组件。

## 2. 用户、文档范围与边界

### 2.1 目标用户

主要用户是学生和教师，也兼顾需要快速自查办公文档的普通用户。典型文档包括课程报告、通知、公文式说明、会议纪要、制度文件、项目方案、申请材料和可复用模板。系统不依赖“实习报告”这一固定模板，也不把某个学校、专业或单一行业的章节硬编码为通用标准。

### 2.2 第一版输入范围

- 核心输入：可读取的 `.docx` 文件路径。
- 规则输入：可选的 JSON/YAML 规则文件，以及用户在自然语言中提供的必需章节、字段或格式要求。
- 审计方式：只读解析原文件，报告写入单独的输出位置，不覆盖原文。
- `.doc`、扫描 PDF、纯图片文字、文本框/形状文字、SmartArt、嵌入式 Excel/PPT、批注和修订等复杂对象不作为基础解析对象。若文档中出现这些对象，系统要分别识别并在结果中登记未审计对象，而不是静默忽略。

### 2.3 明确的非目标

第一版不自动改格式、不自动补写章节、不接受未经确认的外部提交、不执行文档中的宏或脚本、不联网上传文档，也不把模型判断当作唯一事实来源。文档内容属于不可信输入，不能因为其中出现“请执行某命令”等文字就改变审计权限或执行流程。

## 3. 三类自然语言意图

三类意图都要能由自然语言触发，并能映射到稳定的 CLI 参数。课程基本验收要求至少有三个直接相关的自然语言意图；这里将三类意图作为固定验收面：

| 意图 | 示例请求 | 计划映射 | 主要结果 |
| --- | --- | --- | --- |
| 完整审计 | “全面检查这份 Word，告诉我结构、空字段和格式问题” | `full` | 综合问题、统计和未审计对象 |
| 结构审计 | “只看标题层级，并按我给的章节清单检查缺项” | `structure` | 标题树、章节缺失/顺序/层级问题 |
| 字段+格式审计 | “检查空白项、占位符和文档内部格式是否统一” | `fields_format` | 空字段、占位符、主导格式异常 |

当用户没有提供必需章节清单时，系统不得自行假定“通用文档”有固定章节。自然语言层应提示用户补充清单；若用户仍要求继续，则结果中明确记录“未指定章节标准”，并只报告可由文档自身结构推断的异常。

## 4. 审计覆盖与结果模型

### 4.1 基础覆盖对象

基础审计计划覆盖以下内容：

1. 正文段落：文本、空段落、常见占位符、段落样式和基础段落格式。
2. 表格及单元格：单元格文本、空单元格、占位符、单元格内段落和可观察的基础格式。
3. 页眉与页脚：文本、空字段/占位符、标题或段落格式的基础一致性。
4. 标题样式和基础段落格式：标题样式的层级关系、同类内容的内部主导样式、显著的字体/字号/对齐/缩进/间距不一致。

“格式正确”不等同于强制使用宋体、小四等固定规范。默认规则以文档内部的主导样式和结构一致性为基准；学校、教师或用户提供的具体规则可以通过配置加入审计。

### 4.2 问题严重级别

- `error`：文件无法解析、必需章节缺失、用户明确要求的关键字段为空等会直接影响交付的问题。
- `warning`：标题层级异常、占位符、格式离群、表格空项，以及未审计对象等需要人工处理但不一定导致文件不可用的问题。
- `info`：一般性的改进建议、未指定标准的提示、低风险的一致性建议。

严重级别是规则输出的一部分，不由模型随意改写。若模型参与解释，必须保留确定性规则产生的证据和原始级别。

### 4.3 JSON 主输出

计划中的 JSON 顶层结构如下；字段名在实现前如有必要只做向后兼容的增补：

```json
{
  "schema_version": "0.1",
  "audit_target": {"path": "example.docx", "format": "docx"},
  "mode": "full",
  "scope": {"paragraphs": true, "tables": true, "headers_footers": true},
  "summary": {"error": 0, "warning": 0, "info": 0},
  "findings": [
    {
      "id": "F-001",
      "severity": "warning",
      "rule_id": "structure.heading_level",
      "location": {"part": "body", "paragraph_index": 12, "heading_path": ["第二章"]},
      "evidence": "Heading 3 直接出现在 Heading 1 后",
      "message": "标题层级存在跳级",
      "suggestion": "检查是否缺少中间层级，或在规则配置中声明允许的层级关系"
    }
  ],
  "unsupported_objects": [
    {
      "id": "U-001",
      "severity": "warning",
      "object_type": "text_box",
      "location": {"part": "body", "xml_hint": "..."},
      "count": 1,
      "reason": "第一版解析器不读取文本框中的文字",
      "impact": "文本框中的标题或字段可能未参与审计",
      "suggestion": "将文字移入正文，或人工检查后再提交"
    }
  ],
  "metrics": {"elapsed_ms": 0, "input_chars_seen": 0, "model_calls": 0},
  "errors": []
}
```

每个 `finding` 必须有可定位的结构化位置、证据和建议。每一种未审计对象必须单独形成 `unsupported_objects` 条目，至少带有对象类型、位置、数量、原因、影响和建议；不能只返回“存在未审计对象”这一句总括信息。Markdown/终端输出只是 JSON 的人类可读投影，不得丢失上述关键信息。

## 5. 系统架构与工作流

```text
用户自然语言
    ↓
离线意图识别/参数整理（模型可插拔）
    ↓
Skill：校验路径、模式、规则与安全边界
    ↓
Python CLI：独立可运行、结构化日志、确定性退出码
    ↓
python-docx：读取正文、表格、页眉、页脚和样式
    ↓
规则引擎：结构 / 字段 / 格式 / 未审计对象
    ↓
JSON 主结果 + Markdown/终端摘要
```

自然语言层默认走离线、低依赖路径：关键词和明确参数可以直接映射到三类意图；模型适配器只负责把复杂请求转换为同一份结构化参数，不直接访问文档底层、不直接改变严重级别、不绕过确认规则。核心 CLI 不依赖在线模型或 API 密钥，便于演示、测试和复现。

### 5.1 计划中的参数

- `--input PATH`：待审计 `.docx`，只读。
- `--mode full|structure|fields_format`：审计模式。
- `--required-sections FILE`：用户提供的必需章节列表；不提供则不假定固定模板。
- `--rules FILE`：自定义规则配置。
- `--format json|markdown|terminal`：结果投影，默认保留 JSON 主结果。
- `--output PATH`：单独的报告输出路径；若路径覆盖输入文件或涉及外部动作，应拒绝或要求明确确认。

实际命令会在 Phase2 脚本完成后冻结并补充到 README、Skill 和测试中。

### 5.2 规则配置

默认规则只包含通用、可解释的检查；站点或用户特定的章节、必填项和格式要求放进配置文件。配置需要有版本、启用规则、严重级别覆盖和可读说明。规则解析失败时返回结构化错误，不能静默退回到一个用户不知道的标准。

## 6. 安全、隐私与低 token 设计

1. 最小权限：核心程序只需要读取输入文档和写入用户明确指定的独立报告位置。
2. 风险确认：不执行删除、移动、覆盖原文、外部提交、桌面点击或网络上传；若未来增加这些动作，必须在动作前展示预览并取得明确确认。
3. 文档隔离：宏、嵌入脚本和文档中的指令文字只当作数据，不执行。日志默认不打印全文和敏感字段，不记录 API key、密码或令牌。
4. 低 token：先由 Python 解析、计数、筛选和压缩为结构化摘要，再把必要证据交给模型；没有模型时仍完成确定性基础审计。指标至少记录输入对象数、发现数、模型调用次数和耗时，并用一个对照实验验证优化效果。
5. 许可证：使用第三方库和数据集时记录名称、版本、许可证及用途；不把许可证不清楚的原始文档放进公开仓库。

## 7. 测试数据与公开数据策略

测试集采用“真实公开文档 + 可控缺陷变体 + 标签/期望结果”的组合：

- 公开文档作为真实排版和结构分布的外部评估语料；优先考虑 Hugging Face 的 `superdoc-dev/docx-corpus`、DocxCorp 的元数据/下载入口以及 WordScape 的公开项目资料。
- 下载前逐文件核对来源、许可、是否允许再分发和是否包含个人敏感信息。候选来源只代表检索入口，不代表所有原始文件都可以直接提交到仓库。
- 仓库只提交许可明确、允许再分发且完成脱敏的少量样例；其他文档放在仓库外，并在 manifest 中记录 URL、获取时间、SHA-256、许可证、引用方式和本地是否存在。
- 用脚本从许可明确的基准文档生成标题跳级、缺章节、空单元格、占位符和格式离群等受控变体，并保存期望标签。这样在没有公开原文或许可发生变化时仍能重复核心回归测试。
- 禁止把实习同学的个人文档、真实姓名/联系方式、真实密钥或许可证不明的下载文件直接加入 Git。

候选资料入口：

- <https://huggingface.co/datasets/superdoc-dev/docx-corpus>
- <https://docxcorp.us/download>
- <https://github.com/DS3Lab/WordScape>

这些链接在实现阶段要重新核对页面上的当前许可和下载条款，并把核对结果写入数据清单。

## 8. 测试与课程验收映射

课程最低要求将逐项落到可运行证据：

| 课程要求 | 阶段1设计映射 | 后续证据 |
| --- | --- | --- |
| 至少3个直接相关自然语言意图 | 完整、结构、字段+格式三类意图 | 3个自然语言命令的 CLI/Agent 测试 |
| 至少1个真实 Python 开源项目 | 选用 `python-docx` | README 写名称、版本、许可证、用途 |
| Skill/等价工具说明 | 根目录 `SKILL.md` 与 `agents/openai.yaml` | 触发、参数、调用、结果格式、至少2个例子 |
| 脚本可独立运行 | 规划离线 Python CLI | 新环境安装依赖后运行 smoke test |
| 5–10 个测试 | 规划正常、边界、异常和安全用例 | pytest 汇总与失败样例 |
| 日志无密钥 | 设计脱敏日志 | 日志扫描和敏感字符串回归测试 |
| 低 token/性能优化 | 先本地解析和结构化压缩 | 模型调用/耗时/输入规模对照数据 |
| 高风险操作确认 | 只读基线，输出与原文分离 | 覆盖、删除、上传等拒绝/确认测试 |

目标测试数量为 8 个左右，覆盖：正常通用文档、空段落/空单元格、标题跳级、用户指定缺章节、未指定标准、不可解析文件、含未审计对象的文档、报告路径安全和日志脱敏。具体数量可在实现后保持在课程要求的 5–10 个可审计范围内。

## 9. 15 天推进与实习记录

以下是按课程验收节奏安排的 15 天主线。每天实际完成后要在实习手册中写一篇第一人称记录，单篇不少于 400 字；记录要写当天做了什么、遇到的问题、解决过程、学到的内容和下一步计划，不用虚构没有发生的实验或成果。

| 天数 | 项目工作 | 当日记录素材 |
| --- | --- | --- |
| 第1天 | 阅读通知、任务书，比较攻防/智能体选题并确定 #03 | 选题理由、课程约束 |
| 第2天 | 建立本地 Skill 仓库，冻结范围和架构 | 初始化、取舍、遇到的工具问题 |
| 第3天 | 设计输入参数、结果 schema 和规则配置 | 为什么 JSON 主输出、如何定位问题 |
| 第4天 | 实现 `.docx` 基础读取和文档部件遍历 | python-docx API 与异常 |
| 第5天 | 实现结构审计 | 标题树、跳级、用户章节清单 |
| 第6天 | 实现字段和占位符审计 | 空段落、空单元格、页眉页脚 |
| 第7天 | 实现基础格式一致性审计 | 主导样式、离群样式、避免硬编码 |
| 第8天 | 实现未审计对象检测与逐项告警 | 对象位置、影响和建议 |
| 第9天 | 完成三类自然语言意图和 Skill 调用说明 | 离线入口与模型可插拔 |
