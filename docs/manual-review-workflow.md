# 本地样例复核流程

依据任务书第 2、5 页，课程不强制使用 nanobot。第 03 题基础任务是标题层级、空字段、缺失章节和基础格式问题，自定义审计规则是可选功能；PII 检测不在该题基础任务中。

交付范围为通用 Word .docx 质量审计 Skill，配套独立 Python CLI。通用指文档用途不受单一模板限制、业务规则可配置、核心处理不绑定宿主；不表示覆盖全部 Office 文件格式或全部审计需求。

选择现有智能体作为入口，优先在 Codex 中验证自然语言理解、Skill 调用、脚本执行和结果解释。Claude Code 可作为第二个宿主验证；未经实际运行不宣称兼容测试通过。无需为本项目安装 nanobot 或增加 MCP 服务。

## 人工复核

1. 工具先为 01–12 号样例生成逐条问题、位置和未审计对象的 Markdown 报告，存放于仓库外 external-samples/review-reports。
2. 人工对照原文和报告，记录误报、漏报及定位是否足够具体。可采用“文件编号 / 问题编号 / 判定 / 理由”的反馈形式。
3. 标题跳级须结合文档实际结构判断；空段落、空单元格及格式差异可能是有意设计；缺失章节仅按明确提供的标准验收。
4. 对未审计对象，检查报告列出的类型和位置能否找到该对象，记录内容是否影响结论。

Word 页面上的一级编号、自然段和 OOXML 段落节点并不一定一一对应，例如编号项中的 a、b、c 子项也可能分别占用内部段落节点。因此报告不得把 `paragraph_index` 转述成“正文第 N 段”。核对空白段落时，应在 Word 的“开始”选项卡开启“显示/隐藏编辑标记(¶)”，再按报告给出的前后可见文字、连续空白总数和组内次序查找；`paragraph_index` 只保留为技术定位。格式离群报告必须同时提供段落原文和“主导格式 / 本段格式”的差异；它表示需要复核，不等于格式必然错误。

现有脚本不检测 PII，用户已观察到多数候选含个人信息。该观察不能算作程序检测结果，也不应要求用户先逐个整理所有个人信息。若后续增加 PII 检测，应单独设置测试标签和检测范围。

## 交付与数据

原始文档以及可能含正文片段的详细审计报告仅保存在仓库外，不作为 GitHub 交付物。代码公开前检查代码、合成测试、说明材料及历史是否含不应公开的内容。真实样例的再分发核验 pending 不阻塞代码开发和质量评估；已知未经授权的敏感个人数据不纳入测试。

原有 manifest 的 pending/verified 保留其发布核验含义，不能代表规则正确率或样例是否解析成功。课程演示和公开复现使用合成文档。
